# 검색 결과 화면 진입 부하 테스트: dev.imhungry.click 기준선 (가상 사용자(VU) 1,000명 목표)

상태: 초안 · 측정 시각: 2026-11-05 17:07:37–17:09:19

- 환경: `https://dev.imhungry.click`. k6는 집 회선에서 인터넷을 거쳐 보냈으므로 응답 시간에 그 왕복 시간이 들어 있습니다.
- 근거 자료: 스크립트 [`scenarios/search/search-page-users.js`](../../../scenarios/search/search-page-users.js), 시간대별 표는 [`tools/timeline.py`](../../../tools/timeline.py)로 만들었습니다. API별 p95는 k6가 측정 중에 보낸 지표(Prometheus)에서 뽑았습니다. 원본 결과 파일은 저장소에 두지 않습니다.
- 미정 항목: 합격선, 측정한 앱 커밋 해시.

## 1. 대상

비로그인 사용자가 검색어로 검색 결과 화면을 열 때 화면이 보내는 요청입니다. dev.imhungry.click 화면을 브라우저로 열어 확인했습니다.

| 순서 | 요청 | 응답 | 내용 |
|---|---|---|---|
| 1 | GET /api/members/me | 401 | 로그인 확인 |
| 2 | POST /api/auth/refresh | 401 | 토큰 갱신 시도 |
| 3 | GET /api/search/suggestions?keyword=… | 200 | 검색어 자동완성 |
| 3 | GET /api/search/recipes?sort=RELEVANCE&keyword=…&page=1&size=8 | 200 | 레시피 검색 |
| 3 | GET /api/search/products?sort=RELEVANCE&keyword=…&page=1&size=16 | 200 | 상품 검색 |
| 3 | GET /api/recipes/classifications | 200 | 레시피 분류 |

- 1과 2는 차례로, 3의 네 요청은 동시에 보냅니다.
- 1과 2의 401은 비로그인 화면의 정상 응답이라 실패로 세지 않았습니다.

## 2. 측정 조건

- dev.imhungry.click의 데이터와 검색 색인을 그대로 썼습니다.
- 검색어는 `대파`, `두부`, `계란`, `된장`, `김치`, `삼겹살`, `밀키트` 중에서 매번 무작위로 골랐습니다.
- 가상 사용자(VU) 1명이 검색 결과 화면을 열고 1–3초 쉰 뒤 다시 여는 것을 반복합니다(가상 사용자 수 고정 방식). 실제 사용자 수와 같지 않습니다. 한 번 열 때 요청 6건이므로 1,000명이면 이론상 초당 약 2,800건입니다.
- 브라우저는 로그인 확인 전에 3의 요청을 한 번 보냈다가 취소하고 다시 보냅니다. 이 측정에서는 한 번만 보냈습니다.
- 측정 전에 10명, 30초로 먼저 돌려 확인했습니다(690건, p95 93ms, 실패 0%, 최대 5.53초 1건).

## 3. 부하 조건

| 항목 | 값 |
|---|---|
| 가상 사용자 | 0 → 100명(30초) → 500명(60초) → 1,000명(60초) → 1,000명 유지(120초) → 0명(30초) |
| 자동 중단 | 실패율 5% 초과 또는 p95 2초 초과 (시작 30초 뒤부터, 시작부터 쌓인 전체 요청 기준) |
| 반복 | 1회 |


## 5. 결과

시작 1분 42초, 가상 사용자 약 600명에서 p95가 2초를 넘어 자동 중단됐습니다. 그때까지 37,590건을 보냈고, 실패는 10건(0.02%)이었습니다. 전체 구간을 합친 값은 p50 367ms, p95 2.11초, p99 5.85초, 최대 9.29초입니다.

### 5-1. 구간별 요약

| 구간 | 가상 사용자 | 초당 요청 | p50 | p95 |
|---|---|---|---|---|
| 0–40초 | 29–159 | 58–387 | 23–34ms | 52–181ms |
| 50–80초 | 226–426 | 530–570 | 65–652ms | 487–1,322ms |
| 90초 | 492 | 482 | 1,201ms | 2,025ms |
| 100초 | 574 | 197 | 3,378ms | 6,410ms |

- 가상 사용자 약 160명(40초)까지는 p50이 23–34ms였습니다.
- 초당 요청은 가상 사용자 약 230명(50초)부터 530–570건에서 더 늘지 않았습니다. 가상 사용자가 늘어난 만큼 응답 시간이 길어졌습니다.
- 100초에는 초당 요청이 197건으로 줄고 p50이 3.4초가 됐습니다.

### 5-2. API별 p95 (시작부터 쌓인 값)

| 경과(초) | 가상 사용자 | 로그인 확인 | 토큰 갱신 | 자동완성 | 레시피 검색 | 상품 검색 | 레시피 분류 |
|---|---|---|---|---|---|---|---|
| 10 | 29 | 35ms | 16ms | 43ms | 72ms | 61ms | 26ms |
| 40 | 159 | 31ms | 34ms | 88ms | 148ms | 149ms | 46ms |
| 60 | 292 | 93ms | 118ms | 705ms | 798ms | 776ms | 117ms |
| 80 | 426 | 443ms | 453ms | 1,028ms | 1,409ms | 1,165ms | 466ms |
| 100 | 574 | 1,192ms | 1,186ms | 1,529ms | 1,818ms | 1,666ms | 1,176ms |

- 이 표의 값은 그 시점까지 쌓인 요청 전체의 p95입니다. k6가 Prometheus로 보낸 API별 지표가 누적값이라 구간별 값은 뽑을 수 없었습니다.
- 검색 세 요청(자동완성, 레시피 검색, 상품 검색)이 처음부터 다른 요청보다 길었고, 60초(약 290명)에 700–800ms로 먼저 올랐습니다. 같은 시점 로그인 확인, 토큰 갱신, 레시피 분류는 93–118ms였습니다.
- 80초(약 430명)부터 여섯 요청이 모두 함께 길어졌습니다.
