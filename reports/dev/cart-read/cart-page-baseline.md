# 장바구니 화면 진입 부하 테스트: dev.imhungry.click 기준선 (가상 사용자(VU) 1,000명 목표)

상태: 초안 · 측정 시각: 2026-11-05 23:24:31–23:27:01 (준비 단계 23:22:48부터) · 도메인 담당자: 장준혁

- 환경: `https://dev.imhungry.click`. k6는 집 회선에서 인터넷을 거쳐 보냈으므로 응답 시간에 그 왕복 시간이 들어 있습니다.
- 근거 자료
  - 스크립트: [`scenarios/cart-read/cart-page.js`](../../../scenarios/cart-read/cart-page.js)
  - 테스트 회원 준비: [`scenarios/dev-prep/members.js`](../../../scenarios/dev-prep/members.js)
  - k6 결과 화면: [`cart-page-20261105-232248.html`](cart-page-20261105-232248.html) (내려받아 브라우저로 엽니다)
  - 10초 단위 표: [`tools/timeline.py`](../../../tools/timeline.py)로 만들었습니다
  - API별 p95: 측정 중에 k6를 실행한 컴퓨터의 로컬 Prometheus로 보낸 요청별 값에서 뽑았습니다
- 미정 항목: 합격선, 측정한 앱 커밋 해시.

## 1. 대상

로그인한 회원이 장바구니 화면을 열 때 화면이 보내는 요청입니다.

| 순서 | 요청 | 응답 | 내용 |
|---|---|---|---|
| 1 | GET /api/members/me | 200 | 로그인 확인 |
| 2 | GET /api/cart-items | 200 | 장바구니 목록 |

## 2. 측정 조건

- 테스트 회원 1,000명(`loadtest-1`–`loadtest-1000@example.com`)을 dev.imhungry.click에 가입시켜 썼습니다. 가상 사용자 1명이 회원 1명을 맡습니다.
- 회원마다 장바구니에 상품 3개(상품 16·17·19, 각 1개)를 담아 둔 상태입니다.
- 가상 사용자(VU) 1명이 장바구니 화면을 열고 1–3초 쉰 뒤 다시 여는 것을 반복합니다(가상 사용자 수 고정 방식). 실제 사용자 수와 같지 않습니다. 한 번 열 때 요청 2건이므로 1,000명이면 이론상 초당 약 1,000건입니다.
- 측정 전에 준비 단계에서 1,000명이 로그인했습니다(약 1분 40초). 이 로그인 요청(p95 421ms)도 자동 중단 기준인 전체 p95에 들어갑니다.
- 측정 전에 10명, 30초로 먼저 돌려 확인했습니다(313건, p95 119ms, 실패 0%).

## 3. 부하 조건

| 항목 | 값 |
|---|---|
| 가상 사용자 | 0 → 100명(30초) → 500명(60초) → 1,000명(60초) → 1,000명 유지(120초) → 0명(30초) |
| 자동 중단 | 실패율 5% 초과 또는 p95 2초 초과 (시작 30초 뒤부터, 시작부터 쌓인 전체 요청 기준) |
| 반복 | 1회 |

## 4. 실행 방법

```bash
BASE_URL=https://dev.imhungry.click k6 run -e MEMBERS=1000 scenarios/dev-prep/members.js
BASE_URL=https://dev.imhungry.click ./tools/run.sh scenarios/cart-read/cart-page.js
python3 tools/timeline.py results/dev/cart-page-<시각>.html
```

## 5. 결과

측정 2분 36초, 가상 사용자가 1,000명에 닿은 직후 p95가 2초를 넘어 자동 중단됐습니다. 장바구니 화면 요청 40,697건이 모두 200이었습니다(실패 0%). 준비 단계를 합친 전체 값은 p50 325ms, p95 2.01초, p99 2.51초, 최대 4.15초입니다.

### 5-1. 구간별 요약

| 구간 | 가상 사용자 | 초당 요청 | p50 | p95 |
|---|---|---|---|---|
| 20–70초 | 44–321 | 34–287 | 28–38ms | 35–85ms |
| 80–100초 | 388–526 | 331–356 | 56–351ms | 235–825ms |
| 110–160초 | 610–1,000 | 338–355 | 665–1,834ms | 1,481–2,631ms |

- 가상 사용자 약 320명(초당 약 290건)까지는 p50이 28–38ms였습니다.
- 초당 요청은 가상 사용자 약 390명(80초)부터 331–356건에서 더 늘지 않았습니다. 가상 사용자가 늘어난 만큼 응답 시간이 길어졌습니다.
- 10초 구간은 첫 구간에 준비 단계의 마지막 요청이 섞여 있습니다.

### 5-2. API별 p95 (시작부터 쌓인 값)

| 경과(초) | 가상 사용자 | 로그인 확인 | 장바구니 목록 |

| 30 | 121 | 30ms | 39ms |
| 60 | 321 | 57ms | 73ms |
| 90 | 526 | 535ms | 564ms |
| 120 | 776 | 1,355ms | 1,393ms |
| 150 | 1,000 | 2,016ms | 2,046ms |

- 이 표의 값은 그 시점까지 쌓인 요청 전체의 p95입니다. k6가 Prometheus로 보낸 API별 지표가 누적값이라 구간별 값은 뽑을 수 없었습니다.
- 두 요청이 함께 올랐고, 장바구니 목록이 로그인 확인보다 30–40ms쯤 길었습니다.
