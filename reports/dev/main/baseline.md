# 메인 화면 진입 부하 테스트: dev.imhungry.click 기준선 (가상 사용자(VU) 1,000명 목표)

상태: 초안 · 측정 시각: 2026-11-05 14:59:27–15:01:43

- 환경: `https://dev.imhungry.click`. k6는 집 회선에서 인터넷을 거쳐 보냈으므로 응답 시간에 그 왕복 시간이 들어 있습니다.
- 근거 자료: 스크립트 [`scenarios/main/main-page-users.js`](../../../scenarios/main/main-page-users.js), 시간대별 표는 [`tools/timeline.py`](../../../tools/timeline.py)로 만들었습니다. API별 p95는 k6가 측정 중에 보낸 지표(Prometheus)에서 뽑았습니다. k6 결과 화면은 [`main-page-users-20261105-145927.html`](main-page-users-20261105-145927.html)입니다(내려받아 브라우저로 엽니다).
- 미정 항목: 합격선, 측정한 앱 커밋 해시.

## 1. 대상

비로그인 사용자가 메인 화면을 열 때 화면이 보내는 요청입니다. dev.imhungry.click 화면을 브라우저로 열어 확인했습니다.

| 순서 | 요청 | 응답 | 내용 |
|---|---|---|---|
| 1 | GET /api/members/me | 401 | 로그인 확인 |
| 2 | POST /api/auth/refresh | 401 | 토큰 갱신 시도 |
| 3 | GET /api/search/popular | 200 | 인기 검색어 |
| 3 | GET /api/sales/popular | 200 | 지금 뜨는 할인 |
| 3 | GET /api/recipes/popular?size=6 | 200 | 이번 달 많이 만든 레시피 |

- 1과 2는 차례로, 3의 세 요청은 동시에 보냅니다.
- 1과 2의 401은 비로그인 화면의 정상 응답이라 실패로 세지 않았습니다.

## 2. 측정 조건

- dev.imhungry.click 데이터를 그대로 썼습니다.
- 가상 사용자(VU) 1명이 메인 화면을 열고 1–3초 쉰 뒤 다시 여는 것을 반복합니다(가상 사용자 수 고정 방식). 실제 사용자 수와 같지 않습니다. 한 번 열 때 요청 5건이므로 1,000명이면 이론상 초당 약 2,300건입니다.
- 브라우저는 로그인 확인이 끝나기 전에 3의 요청을 한 번 보냈다가 취소하고 다시 보냅니다. 이 측정에서는 한 번만 보냈습니다.
- 측정 전에 10명, 30초로 먼저 돌려 확인했습니다(625건, p95 42ms, 실패 0%).

## 3. 부하 조건

| 항목 | 값 |
|---|---|
| 가상 사용자 | 0 → 100명(30초) → 500명(60초) → 1,000명(60초) → 1,000명 유지(120초) → 0명(30초) |
| 자동 중단 | 실패율 5% 초과 또는 p95 2초 초과 (시작 30초 뒤부터, 시작부터 쌓인 전체 요청 기준) |
| 반복 | 1회 |


## 5. 결과

시작 2분 16초, 가상 사용자 약 880명에서 p95가 2초를 넘어 자동 중단됐습니다. 그때까지 66,790건을 보냈고, 실패는 17건(0.02%)으로 모두 502였습니다. 전체 구간을 합친 값은 p50 59ms, p95 2.36초, p99 5.24초, 최대 11.37초입니다.
