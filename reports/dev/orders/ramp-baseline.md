# 주문 부하 테스트: dev.imhungry.click 기준선 (가상 사용자(VU) 1,000명 목표)

상태: 초안 · 측정 시각: 2026-11-05 23:33:06–23:34:27 (준비 단계 23:31:33부터) · 도메인 담당자: 장준혁

- 환경: `https://dev.imhungry.click`. k6는 집 회선에서 인터넷을 거쳐 보냈으므로 응답 시간에 그 왕복 시간이 들어 있습니다.
- 근거 자료
  - 스크립트: [`scenarios/orders/order-ramp.js`](../../../scenarios/orders/order-ramp.js)
  - 테스트 회원 준비: [`scenarios/dev-prep/members.js`](../../../scenarios/dev-prep/members.js)
  - k6 결과 화면: [`order-ramp-20261105-233133.html`](order-ramp-20261105-233133.html) (내려받아 브라우저로 엽니다)
  - 10초 단위 표: [`tools/timeline.py`](../../../tools/timeline.py)로 만들었습니다
  - API별 p95: 측정 중에 k6를 실행한 컴퓨터의 로컬 Prometheus로 보낸 요청별 값에서 뽑았습니다
- 미정 항목: 합격선, 측정한 앱 커밋 해시.

## 1. 대상

로그인한 회원이 장바구니에서 주문하고, 주문 확인 화면에서 결제하지 않고 나가는 흐름입니다.

| 순서 | 요청 | 응답 | 내용 |
|---|---|---|---|
| 1 | GET /api/members/me | 200 | 장바구니 화면의 로그인 확인 |
| 2 | GET /api/cart-items | 200 | 장바구니 목록 |
| 3 | POST /api/orders | 201 | 주문하기 |
| 4 | GET /api/orders/{orderId}/checkout | 200 | 주문 확인 화면 |
| 5 | PATCH /api/orders/{orderId}/cancel | 200 | 나가기 |

- 주문하기는 재고를 줄이고, 나가기는 주문을 지우고 재고를 되돌립니다. 장바구니 항목은 주문 뒤에도 남아 다음 반복에 다시 씁니다.

## 2. 측정 조건

- 테스트 회원 1,000명을 썼습니다. 가상 사용자 1명이 회원 1명을 맡습니다.
- 주문 한 건에 테스트 상품 2개(밀키트 29, 재료 30)를 1개씩 담습니다. 두 상품은 재고 2,000개, 행사 없음으로 이 측정을 위해 등록했습니다.
- 모든 주문이 같은 두 상품의 재고를 줄입니다. 한 상품에 주문이 몰리는 상황입니다.
- 가상 사용자(VU) 1명이 위 흐름을 한 번 하고 1–3초 쉰 뒤 다시 하는 것을 반복합니다(가상 사용자 수 고정 방식). 실제 사용자 수와 같지 않습니다. 한 번에 요청 5건이므로 1,000명이면 이론상 초당 약 2,000건입니다.
- 측정 전에 준비 단계에서 1,000명이 로그인했습니다(약 1분 30초). 이 로그인 요청(p95 399ms)도 자동 중단 기준인 전체 p95에 들어갑니다.
- 측정 전에 10명, 30초로 먼저 돌려 확인했습니다(666건, p95 53ms, 실패 0%).

## 3. 부하 조건

| 항목 | 값 |
|---|---|
| 가상 사용자 | 0 → 100명(30초) → 500명(60초) → 1,000명(60초) → 1,000명 유지(120초) → 0명(30초) |
| 자동 중단 | 실패율 5% 초과 또는 p95 2초 초과 (시작 30초 뒤부터, 시작부터 쌓인 전체 요청 기준) |
| 반복 | 1회 |

## 4. 실행 방법

```bash
BASE_URL=https://dev.imhungry.click ./tools/run.sh scenarios/orders/order-ramp.js
python3 tools/timeline.py results/dev/order-ramp-<시각>.html
```

## 5. 결과

측정 1분 29초, 가상 사용자 약 490명에서 p95가 2초를 넘어 자동 중단됐습니다. 흐름의 요청 15,622건이 모두 기대한 응답이었습니다(실패 0%). 주문은 3,117건 만들어졌습니다. 준비 단계를 합친 전체 값은 p50 303ms, p95 2.01초, p99 2.53초, 최대 3.68초입니다.

### 5-1. 구간별 요약

| 구간 | 가상 사용자 | 초당 요청 | p50 | p95 |
|---|---|---|---|---|
| 20–30초 | 44–78 | 78–152 | 33–35ms | 98–112ms |
| 40–50초 | 123–189 | 204–209 | 88–370ms | 274–767ms |
| 60–90초 | 256–456 | 202–208 | 677–1,625ms | 1,305–2,541ms |

- 가상 사용자 약 80명(초당 약 150건)까지는 p50이 33–35ms였습니다.
- 초당 요청은 가상 사용자 약 120명(40초)부터 202–209건에서 더 늘지 않았습니다. 가상 사용자가 늘어난 만큼 응답 시간이 길어졌습니다.
- 10초 구간은 첫 구간에 준비 단계의 마지막 요청이 섞여 있습니다.

### 5-2. API별 p95 (시작부터 쌓인 값)

| 경과(초) | 가상 사용자 | 로그인 확인 | 장바구니 목록 | 주문하기 | 주문 확인 화면 | 나가기 |
|---|---|---|---|---|---|---|
| 30 | 123 | 186ms | 201ms | 265ms | 186ms | 266ms |
| 60 | 323 | 1,397ms | 1,377ms | 1,470ms | 1,370ms | 1,436ms |
| 90 | 489 | 2,144ms | 2,068ms | 2,261ms | 2,170ms | 2,165ms |

- 이 표의 값은 그 시점까지 쌓인 요청 전체의 p95입니다. k6가 Prometheus로 보낸 API별 지표가 누적값이라 구간별 값은 뽑을 수 없었습니다.
- 다섯 요청이 함께 올랐습니다. 주문하기와 나가기가 조회 요청보다 30–100ms쯤 길었습니다.

### 5-3. 측정 뒤 남은 것

- 중단 때 주문하기까지만 하고 나가지 못한 주문 164건이 결제 대기로 남았고, 그만큼 두 상품의 재고가 줄어 있었습니다(2,000개 → 1,836개).
