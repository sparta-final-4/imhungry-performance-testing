## 1. 목표

회원 100명이 같은 순간 같은 상품 하나를 1개씩 주문했을 때 아래를 모두 만족한다.

| 항목 | 기준 |
|---|---|
| 서버 오류 | 5xx 0건, 그 밖의 응답(시간 초과 포함) 0건 |
| 재고 | 성공 건수만큼만 줄고 음수가 없다(DB 최종 상태로 확인) |
| 응답 시간 | 주문하기 p95 1초 이하 |

전체 처리 시간(같은 순간 보낸 시각부터 마지막 응답까지)은 기준이 아니라 기록합니다. 100건을 같은 순간 보내므로 주문하기 응답 시간의 최대값과 같습니다.

## 2. 대상과 측정 조건

| 항목 | 내용 |
|---|---|
| API | POST /api/orders |
| 회원 | 테스트 회원 100명(`loadtest-1`–`loadtest-100`), 가상 사용자 1명이 회원 1명을 맡음 |
| 보내는 방식 | 준비(로그인, 장바구니 담기)를 마친 뒤 정해 둔 같은 시각에 100명이 한 번씩 보냄 |
| 경우 A | 상품 31(재고 100,000개). 100건 모두 성공을 기대 |
| 경우 B | 상품 32. 회차마다 시작 전에 관리자로 재고를 10개로 맞춤. 성공 10건, 품절 거절(409) 90건을 기대 |
| 상품 | 일반 테스트 상품, 행사 없음 |
| 뒷정리 | 주문 20초 뒤 성공한 주문을 모두 나가기(취소)해 재고를 되돌림 |
| DB 확인 | 읽기 전용 조회로 주문 전, 주문 12초 뒤, 취소 뒤에 상품 재고·상태, 그 상품의 결제 대기 주문 수, 재고가 음수인 상품 수를 읽음 |
| 회차 | 경우 A는 예열 1회 뒤 3회, 경우 B는 3회 |

- 예열을 둔 이유: 같은 스크립트를 로컬에서 미리 돌렸을 때 오래 쉬던 앱의 첫 회차(p95 8.07초)와 둘째 회차(p95 2.32초)가 크게 달랐습니다.
- 측정 시작 때 k6를 실행한 컴퓨터의 1분 부하 평균은 20.26(CPU 10개)이었습니다. 서버는 dev에 있으므로 이 값은 k6 쪽(보내기, 받기, 시간 재기)에만 걸리는 조건이고, 한 번에 100건을 보내는 이 측정에서 영향이 있었는지는 확인하지 않았습니다.

## 3. 실행 방법

```bash
BASE_URL=https://dev.imhungry.click ./tools/run.sh -e PRODUCT_ID=31 scenarios/orders/order-same-100.js            # 경우 A
BASE_URL=https://dev.imhungry.click ./tools/run.sh -e PRODUCT_ID=32 -e STOCK=10 scenarios/orders/order-same-100.js  # 경우 B
```

`ADMIN_EMAIL`, `ADMIN_PASSWORD` 환경변수가 필요합니다.

## 5. 분석

- 서버 오류: 7회 700건 모두 응답을 받았고 5xx와 시간 초과는 0건입니다.
- 재고: 경우 A는 4회 모두 100건이 성공했고 재고가 정확히 100개 줄었습니다. 경우 B는 3회 모두 성공이 정확히 10건이었고 재고가 0이 되며 품절로 바뀌었습니다. 초과 판매와 음수 재고는 없었습니다. 취소 뒤에는 재고와 상태가 처음으로 돌아왔습니다.
- 응답 시간: 본 측정 6회의 주문하기 p95는 350–768ms로 모두 1초 이하입니다. 회차별 p95의 가운데 값은 경우 A 503ms, 경우 B 406ms입니다.
- 예열 회차의 p95는 963ms, 최대는 1,020ms로 본 측정보다 길었습니다. 기준(1초)과의 차이는 37ms입니다.
- 경우 A의 p95가 회차마다 350ms, 503ms, 768ms로 두 배 넘게 차이 났습니다. 경우 B는 372–444ms로 차이가 작았습니다.
- 경우 B(90건이 품절 거절)의 p95가 경우 A보다 짧았습니다(가운데 값 406ms 대 503ms).
- 가장 빠른 응답은 37–79ms였습니다. 인터넷 왕복 시간이 들어 있는 값입니다.
