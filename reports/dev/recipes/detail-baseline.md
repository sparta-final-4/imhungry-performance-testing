- 환경: `https://dev.imhungry.click`. k6는 집 회선에서 인터넷을 거쳐 보냈으므로 응답 시간에 그 왕복 시간이 들어 있습니다.
- 근거 자료: 스크립트 [`scenarios/recipes/recipe-detail-users.js`](../../../scenarios/recipes/recipe-detail-users.js), 시간대별 표는 [`tools/timeline.py`](../../../tools/timeline.py)로 만들었습니다. API별 p95는 k6가 측정 중에 보낸 지표(Prometheus)에서 뽑았습니다. k6 결과 화면은 [`recipe-detail-users-20261105-171019.html`](recipe-detail-users-20261105-171019.html)입니다(내려받아 브라우저로 엽니다).
- 미정 항목: 합격선, 측정한 앱 커밋 해시.

## 1. 대상

비로그인 사용자가 레시피 상세 화면을 열 때 화면이 보내는 요청입니다. dev.imhungry.click 화면을 브라우저로 열어 확인했습니다.

| 순서 | 요청 | 응답 | 내용 |
|---|---|---|---|
| 1 | GET /api/members/me | 401 | 로그인 확인 |
| 2 | POST /api/auth/refresh | 401 | 토큰 갱신 시도 |
| 3 | GET /api/recipes/{id} | 200 | 레시피 상세 |
| 3 | GET /api/recipes/{id}/cooking-stats | 200 | 요리 기록 통계 |
| 3 | GET /api/reviews?recipeId={id}&sort=LATEST&size=5&page=1 | 200 | 후기 목록(최신 5개) |

- 1과 2는 차례로, 3의 세 요청은 동시에 보냅니다.
- 1과 2의 401은 비로그인 화면의 정상 응답이라 실패로 세지 않았습니다.

## 2. 측정 조건

- dev.imhungry.click의 레시피 1,693개 중 목록 앞 300개를 시작할 때 받아 두고, 화면을 열 때마다 무작위로 골랐습니다.
- 가상 사용자(VU) 1명이 레시피 상세를 열고 1–3초 쉰 뒤 다시 여는 것을 반복합니다(가상 사용자 수 고정 방식). 실제 사용자 수와 같지 않습니다. 한 번 열 때 요청 5건이므로 1,000명이면 이론상 초당 약 2,300건입니다.
- 브라우저는 로그인 확인 전에 레시피 상세를 한 번 보냈다가 취소하고 다시 보냅니다. 이 측정에서는 한 번만 보냈습니다.
- 측정 전에 10명, 30초로 먼저 돌려 확인했습니다(663건, p95 35ms, 실패 0%).
