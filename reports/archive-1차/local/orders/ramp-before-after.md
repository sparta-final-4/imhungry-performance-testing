## 1. 대상

로그인한 회원이 장바구니에서 주문하고, 주문 확인 화면에서 결제하지 않고 나가는 흐름입니다. 주문 한 건에 테스트 상품 두 개(12, 13)를 1개씩 담고, 모든 주문이 같은 두 상품의 재고를 줄입니다. dev 기준선(`reports/dev/orders/ramp-baseline.md`)과 같은 흐름입니다.

## 2. 측정 조건

- 앱·데이터·검색 서버 컨테이너와 모니터링 서버로 구성한 로컬 환경입니다. 회차 사이에 앱 컨테이너를 새로 띄웠습니다.
- 상품 12번과 13번 재고를 2,000개로 맞추고 결제 대기 주문이 없는 상태에서 시작했습니다.
- 가상 사용자 0 → 100명(30초) → 500명(60초) → 1,000명(60초) → 1,000명 유지(120초) → 0명(30초). 실패율 5% 초과 또는 p95 2초 초과가 30초 뒤부터 이어지면 중단합니다.
- 시작 전 1분 부하 평균은 변경 전 2.83, 변경 후 2.61이었습니다(CPU 10개).
- 회차마다 한 번씩만 돌렸습니다. 같은 앱을 반복했을 때의 편차는 측정하지 않았습니다.

## 3. 결과

두 회차 모두 가상 사용자 1,000명에 도달한 뒤 p95 2초를 넘어 자동 중단됐습니다. 실패율은 둘 다 0%, 서버 오류는 둘 다 0건입니다.

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| 중단까지 걸린 시간 | 3분 34초 | 3분 51초 |
| 전체 요청 수 | 82,967 | 96,409 |
| 반복 수(주문 흐름 완료) | 15,348 | 17,600 |

| 주문하기 초당 최대(20초 이동 평균) | 176.3건 | 166.7건 |
| 나가기 초당 최대(20초 이동 평균) | 175.5건 | 165.7건 |
| 초당 요청 최대(10초 구간) | 938건(가상 사용자 580명) | 893건(가상 사용자 523명) |

- 전체 요청 수와 반복 수는 중단 시각이 달라 비교할 수 없습니다. 중단은 시작부터 쌓인 누적 p95가 2초를 넘을 때 일어나서, 처리량이 아니라 응답 시간이 길어지는 속도와 관계됩니다.
- 처리량이 가장 높았던 구간은 두 회차 모두 가상 사용자 500–600명 근처입니다. 그 뒤 초당 요청이 절반 안팎으로 떨어졌습니다.

- 로그 fsync가 두 회차 모두 초당 약 1,700회에서 더 늘지 않았습니다.

## 4. 해석

- 이 한 쌍의 측정에서는 변경 후 처리량이 변경 전보다 높지 않았습니다. 주문하기 초당 최대는 176.3건에서 166.7건으로 5% 낮았고, 회차 사이 편차를 측정하지 않아 이 차이가 변경 때문인지 알 수 없습니다. 개선은 보이지 않았다고만 말할 수 있습니다.
- 행 잠금 대기와 대기 시간이 전후 같았으므로, 이 로컬 조건에서는 잠금 안에서 쓰는 시간이 줄어든 효과가 처리량에 나타나지 않았습니다.
- 로컬은 앱과 DB 사이 왕복이 거의 없습니다. 이 변경이 줄이는 것은 잠금 안의 SQL 왕복 횟수라서, 이 환경에서 변경 효과가 안 나타난다고 해서 왕복이 긴 환경에서도 같다고 말할 수는 없습니다. 그 환경에서의 효과는 이 측정으로 알 수 없습니다.
- 두 회차의 DB 로그 fsync가 같은 최댓값에서 멈춘 것은 이 로컬 환경에서 처리량을 막는 자원이 잠금이 아니라 커밋(디스크 기록)일 가능성을 보여 주지만, 직접 확인하지는 못했습니다.

## 5. 다음에 할 것

- 같은 앱으로 반복 측정해 회차 사이 편차를 먼저 측정합니다. 편차를 모르면 위 5% 차이를 읽을 수 없습니다.
- 잠금 안의 왕복 횟수가 영향을 주는 환경에서 전후를 다시 측정합니다(dev 배포 뒤 같은 스크립트).
