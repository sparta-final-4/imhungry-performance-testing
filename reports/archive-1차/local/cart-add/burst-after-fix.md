상태: 초안 · 측정일: 2026-11-05 · 도메인 담당자: 장준혁

- 기준선은 [burst-baseline.md](burst-baseline.md)이고 조건은 같습니다(회원 1,000명이 (회원, 상품) 조합을 한 번씩 담기, 초당 50 → 100 → 250 → 500건, 단계마다 15초).
- 개선 전후 앱은 [accuracy-after-fix.md](accuracy-after-fix.md)와 같습니다(`dev` 최신 `a483c962`로 다시 빌드).
- 회차마다 DB에서 항목 수가 성공(201) 응답 수와 같고 수량이 모두 1이며 중복이 없음을 확인했습니다(3회 모두 맞음).
- 근거 자료
  - 스크립트: [`scenarios/cart-add/cart-add-burst.js`](../../../../scenarios/cart-add/cart-add-burst.js)

  - 개선 전 결과 화면: [burst-baseline.md](burst-baseline.md)에 있습니다

## 결과

### 단계별 p95 (3회 중앙값)

| 단계 | 개선 전 | 개선 후 |
|---|---|---|
| 50건 | 6ms | 7ms |
| 100건 | 4ms | 4ms |
| 250건 | 4ms | 5ms |
| 500건 | 7ms | 44ms |

500건 단계의 p99는 59ms에서 139ms, 최대는 164ms에서 317ms로 늘었습니다.

- 5xx와 못 따라간 요청은 전후 모두 0건입니다. 이 시나리오는 같은 회원의 요청이 겹치지 않아 충돌 처리가 일하지 않는 경로입니다.
- 500건 단계의 p95가 7ms에서 44ms로 늘었습니다. 앱 쪽 구간 p95 최대도 6ms에서 85ms로 늘었습니다. 원인은 확인하지 못했습니다(충돌 처리 코드 때문인지, 같은 `dev`에 섞인 다른 변경이나 측정 편차인지 구분하지 못함).
- 요청 1건당 SQL 문은 전후 모두 약 25문입니다.
