# 번개 드롭 등록 부하 테스트: 기준선 (알림 발행)

## 1. 대상

| 항목 | 내용 |
|---|---|
| API | POST /api/admin/sale-events/flash-drop |
| 상황 | 관리자가 번개 드롭을 등록하면 정지되지 않은 일반 회원 전체에게 알림이 만들어짐 |
| 로그인 | 필요 (관리자) |
| 처리 | 등록이 커밋되면 같은 요청 안에서 일반 회원 전체의 알림 요청을 만들어 Kafka에 발행하고 응답함. 소비자가 알림을 한 건씩 저장함 |
| 알림 개수 | 일반 회원 수 × 행사 상품 수 |

## 2. 측정 조건

- 행사 상품 1개를 등록합니다(한정 수량 7개, 상품 16). 시작 시각을 20분 뒤로 잡아 측정 중에 시작 알림이 섞이지 않게 했습니다.
- 일반 회원 수를 약 1천 명(1,016명), 1만 명, 5만 명으로 늘려 측정합니다. 1만·5만 명은 SQL로 테스트 회원을 넣었고, 측정이 끝난 뒤 지웠습니다.
- 알림 저장 시간은 행사 저장 시각부터 마지막 알림 저장 시각까지입니다. DB에 저장된 시각으로 계산합니다.
- 응답이 아니라 DB로 확인했습니다. 저장된 알림 수와 서로 다른 회원 수를 기대값(일반 회원 수)과 비교했습니다.
- 회차마다 되돌리기 SQL로 행사와 알림을 지운 뒤 시작했습니다.

## 3. 부하 조건

| 항목 | 값 |
|---|---|
| 요청 | 등록 1건 (요청을 겹치지 않음) |
| 회원 수 | 1,016명, 10,000명, 50,000명 |
| 반복 | 회원 수마다 3회, 회차 사이 45초 쉼 |

## 4. 실행 방법

```bash
# 회원 수 늘리기(파일 안의 @target을 바꿔서 넣음), 그 뒤 한 회차
DB_USER=<사용자> DB_PASSWORD=<비밀번호> ./tools/run-flash-drop.sh -e ADMIN_PASSWORD=<로컬 관리자 비밀번호>
```

## 5. 결과

### 5-1. 회차별 결과

모든 회차에서 저장된 알림이 기대 개수와 같았고 서로 다른 회원 수도 같았습니다. 유실과 중복은 없었고 5xx도 없었습니다.

| 회원 수 | 회차 | 등록 응답 시간 | 행사 저장부터 마지막 알림 저장까지 | 저장된 알림 | 알림 저장 속도(건/초) |
|---|---|---|---|---|---|
| 1,016 | 1 | 17.6ms | 0.99초 | 1,016 | 1,023 |
| 1,016 | 2 | 19.7ms | 0.87초 | 1,016 | 1,164 |
| 1,016 | 3 | 14.3ms | 0.87초 | 1,016 | 1,171 |
| 10,000 | 1 | 58.9ms | 7.97초 | 10,000 | 1,255 |
| 10,000 | 2 | 43.3ms | 7.84초 | 10,000 | 1,275 |
| 10,000 | 3 | 53.0ms | 7.95초 | 10,000 | 1,258 |
| 50,000 | 1 | 229.0ms | 38.85초 | 50,000 | 1,287 |
| 50,000 | 2 | 279.8ms | 38.68초 | 50,000 | 1,293 |
| 50,000 | 3 | 185.6ms | 38.57초 | 50,000 | 1,296 |

### 5-2. 회원 수별 3회 중앙값

| 회원 수 | 등록 응답 시간 | 알림이 전부 저장될 때까지 | 알림 저장 속도(건/초) |
|---|---|---|---|
| 1,016 | 17.6ms | 0.87초 | 1,164 |
| 10,000 | 53.0ms | 7.95초 | 1,258 |
| 50,000 | 229.0ms | 38.68초 | 1,293 |

- 회원 수가 늘면 등록 응답 시간도 늘었습니다(17.6ms → 53.0ms → 229.0ms). 등록 요청 안에서 회원을 읽고 알림 요청을 만들어 발행하기 때문입니다.
- 알림이 전부 저장될 때까지의 시간은 회원 수에 비례했습니다. 저장 속도는 회원 수와 상관없이 초당 약 1,200–1,300건으로 일정했습니다. 이 환경에서 관찰한 값이며 dev에서도 같다는 보장은 없습니다.
- 회차 사이 편차는 작았습니다(저장 시간 ±1%, 등록 응답 시간은 50,000명에서 186–280ms).

## 6. 다음에 할 것

개선은 코드·쿼리 → 캐시 → 다른 기술 → 대안 순서로 검토하고, 단계마다 같은 조건으로 다시 측정해 목표에 닿으면 멈춥니다. 비교 기준은 고정 속도에서의 p95와 요청 1건당 SQL 문 수입니다.

1. 코드·쿼리: 등록 요청 안에서 회원 전체를 읽고 알림 요청을 만들어 발행하는 구조를 봅니다(회원 수에 따라 응답이 늘어나는 원인). 소비자가 알림을 1건씩 트랜잭션으로 저장하는 구조도 봅니다.
2. 캐시: 해당이 적습니다.
3. 다른 기술: 알림 토픽의 파티션 수와 소비 방식(건별 커밋 대신 묶어 저장)을 확인합니다. 로컬 기본 토픽은 파티션 1개이고 dev의 값은 확인하지 못했습니다.
4. 대안: 등록 응답과 알림 발행을 분리하는 방법, 알림 대상 범위를 정하는 방법을 검토합니다.

시작 시각에 나가는 시작 알림의 저장 시간도 같은 방법으로 측정합니다.
