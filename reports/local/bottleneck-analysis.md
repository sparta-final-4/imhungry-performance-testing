# 개선 방향 분석: 주문·장바구니·지금 뜨는 할인·번개 드롭 알림

상태: 초안 · 분석일: 2026-11-05 · 도메인 담당자: 장준혁

로컬 환경의 CPU 포화나 어느 서버가 먼저 막히는지는 dev에서도 같다는 보장이 없어 근거로 쓰지 않습니다. 이 문서의 근거는 환경이 바뀌어도 그대로인 것입니다: 요청 1건이 보내는 SQL(MySQL 일반 로그), 쿼리 실행 계획(`EXPLAIN`), 코드와 설정의 구조. 개선은 코드·쿼리 → 캐시 → 다른 기술 → 대안 순서로 검토하고, 단계마다 같은 조건으로 다시 측정해 목표에 닿으면 멈춥니다.

## 한눈에 보기

| API | 요청 1건의 작업량 | 코드·쿼리에서 먼저 볼 것 | 캐시 | 다른 기술·대안 |
|---|---|---|---|---|
| GET /api/cart-items | SQL 28문(데이터 8, 트랜잭션 제어 20). 읽기에서도 세션 갱신 UPDATE | 인증 세션 갱신, 트랜잭션 4개로 나뉜 구조, 트랜잭션 제어 문장 | 상품·할인 조회 부분만 후보 | 1·2로 부족할 때 |
| GET /api/sales/popular | 클릭 이력 약 10만 행을 요청마다 집계 | 집계 범위와 필요한 결과 수. 인덱스는 이미 사용 중 | 결과가 모두에게 같아 유력 | 미리 집계(카운터), 집계 기간·정확도 완화 |
| 번개 드롭 알림 | 등록 요청 안에서 회원 전체 조회·발행, 소비자는 알림 1건당 트랜잭션 1번 | 등록 요청의 동기 발행, 건별 저장 | 해당 적음 | 파티션·배치 저장, 발행 분리 |
| POST /api/orders | 정상 주문 SQL 17문(데이터 12) | 거절 요청의 처리 경로, 재고 UPDATE, 장바구니 행 잠금 | 남은 수량 선확인(정확성 유지 조건) | 대기열 등 |
| POST /api/cart-items | 장바구니 조회와 같은 인증·트랜잭션 구조, SQL 약 25문 | 조회와 같음 | 해당 적음 | 필요 시 |

## 1. 장바구니 조회

- **조회 쿼리는 가볍습니다.** 5개 모두 인덱스를 타고(`uk_carts_member_id`, `uk_cart_items_cart_id_product_id` 등) 읽는 행이 1–3개입니다. 쿼리 튜닝의 여지는 작습니다.
- **요청 1건이 SQL 28문을 보냅니다.** 일반 로그로 확인한 내역입니다.
  - 데이터 문장 8개: 인증(세션 조회, 회원 조회, 세션 갱신 UPDATE), 장바구니 항목, 재료 연결, 밀키트 연결, 상품, 진행 중 할인.
  - 트랜잭션 제어 20개(`SET autocommit`, `COMMIT`, `SET SESSION TRANSACTION READ ONLY/READ WRITE`). 요청 1건이 트랜잭션 4개로 나뉘어 각각 5문씩 보냅니다.
- **읽기 요청마다 DB에 씁니다.** 인증 처리(`AuthSessionService.authenticate`)가 세션의 마지막 사용 시각을 갱신하는 UPDATE를 요청마다 보내고 커밋합니다. MySQL 설정이 커밋마다 디스크에 쓰도록(`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`) 되어 있어 가볍지 않습니다.
- **인증이 없는 읽기와 비교했습니다.** 같은 속도(초당 약 535건)에서 인증이 없는 상품 목록(SQL 18문)은 DB 서버 CPU가 약 23%였고 장바구니 조회(SQL 28문)는 약 55%였습니다(이 환경의 관찰). 요청당 작업량이 늘어난 만큼 비용도 늘었습니다.

개선 방향:
1. **코드·쿼리**: 인증 세션 갱신을 요청마다 하지 않는 방법(예: 마지막 갱신 후 일정 시간 안이면 건너뜀), 트랜잭션 수와 트랜잭션 제어 문장을 줄이는 설정을 검토합니다. 인증은 다른 도메인과 함께 쓰는 코드라 영향 범위를 확인해야 합니다.
2. **캐시**: 장바구니는 회원별이고 변경이 잦아 효과가 불확실합니다. 회원과 무관한 상품·할인 조회가 후보입니다.
3. **다른 기술·대안**: 1·2로 목표에 닿지 못할 때 검토합니다.

## 2. 지금 뜨는 할인

- 요청 1건의 데이터 쿼리는 3개입니다: 진행 중 행사, 상품, 최근 7일 검색 클릭 집계. 나머지 SQL은 트랜잭션 제어입니다(총 28문).
- **집계 쿼리가 요청마다 클릭 이력 전체를 읽습니다.** 약 10만 건이 모두 7일 범위에 들어가고, 인덱스(`created_at, product_id`)를 처음부터 끝까지 읽은 뒤 임시 테이블로 묶습니다. `EXPLAIN ANALYZE` 실행 시간은 이 환경에서 약 18ms입니다.
- **인덱스는 이미 쓰고 있습니다.** 커버링 인덱스라 인덱스를 더 만들어도 읽는 행 수가 줄지 않습니다.
- 이 API에는 캐시가 없습니다. 결과가 모든 요청에서 같은데도 요청마다 같은 집계를 반복합니다.

개선 방향:
1. **코드·쿼리**: 집계 범위가 7일 전체여야 하는지, 상위 몇 개만 필요한지 확인합니다. 인덱스 추가로는 해결되지 않습니다.
2. **캐시**: 결과가 모두에게 같아 짧은 시간 캐시가 유력합니다. 갱신 주기를 정해야 합니다.
3. **다른 기술**: 클릭을 미리 집계해 두는 방식(별도 집계 테이블이나 카운터)은 캐시로 부족할 때 검토합니다.
4. **대안**: 집계 기간이나 정확도 요구를 완화(실시간 대신 주기 집계)할 수 있는지 확인합니다.

## 3. 번개 드롭 알림

- **등록 응답이 회원 수에 따라 늘어납니다.** 등록이 커밋되면 같은 요청 스레드가 일반 회원 전체를 읽어 알림 요청을 만들고 Kafka에 발행한 뒤 응답합니다.
- **알림 저장 속도는 소비 방식이 정합니다.** 알림 요청 토픽의 파티션이 로컬 기본 설정으로 1개(`KafkaConfig`)이고, 소비자는 알림 1건마다 트랜잭션을 열어 1행을 저장하고 커밋합니다(오프셋도 1건 단위). 파티션이 1개면 소비자를 늘려도 하나만 일합니다.
- 확인하지 못한 것: dev의 알림 토픽 파티션 수.

개선 방향:
1. **코드·쿼리**: 등록 요청 안에서 회원 전체를 읽고 만드는 구조, 알림을 1건씩 저장하는 구조를 봅니다.
2. **캐시**: 해당이 적습니다.
3. **다른 기술**: 파티션 수와 소비 방식(묶어 저장)은 Kafka 설정 변경이라 dev 값을 확인한 뒤 검토합니다.
4. **대안**: 등록 응답과 알림 발행을 분리하는 방법, 알림 대상 범위를 정하는 방법.

## 4. 주문과 장바구니 담기

- 정상 주문 1건이 보내는 SQL은 17문입니다(일반 로그). 데이터 문장 12개는 인증 3개(세션 조회, 회원 조회, 세션 갱신 UPDATE), 장바구니 행 잠금(`select … for update`) 1개, 장바구니 항목·멱등 확인·상품·진행 중 할인 조회 4개, 쓰기 3개(주문, 주문 항목, 상품 재고 UPDATE)입니다. 트랜잭션이 하나라 트랜잭션 제어는 5문뿐입니다. 같은 데이터를 반복해서 읽지는 않습니다.
- 상품 재고 UPDATE는 재고만이 아니라 상품 행의 컬럼 전체를 갱신하는 문장입니다. 같은 상품에 주문이 몰리면 모든 주문이 같은 행을 갱신하며 순서를 기다립니다.
- 주문은 회원의 장바구니 행을 잠그므로 같은 회원의 요청은 하나씩 순서대로 처리됩니다.
- 몰림 때 요청의 약 90%는 품절·한도 초과로 거절됩니다. 요청 1건당 SQL이 약 16문(Prometheus 집계)으로 정상 주문(17문)과 거의 같아서, 거절 요청도 인증과 조회를 거의 다 거친다고 보입니다. 거절 요청의 문장 내역은 따로 확인하지 않았습니다.
- 장바구니 담기는 조회와 같은 인증·트랜잭션 구조입니다(요청 1건당 SQL 약 25문).

개선 방향:
1. **코드·쿼리**: 거절 요청이 어느 문장까지 가는지 확인하고 품절·한도 초과를 일찍 판단할 수 있는지 봅니다. 재고 UPDATE의 갱신 컬럼 범위와 인증 세션 갱신(장바구니 조회와 공통)을 확인합니다.
2. **캐시**: 번개 드롭 남은 수량 확인을 DB 앞에서 하는 방식이 후보입니다. 초과 판매 0건을 유지하는 것이 조건입니다.
3. **다른 기술·대안**: 1·2로 부족할 때, 몰림 구간을 어떻게 받을지(대기열 등 정책)와 함께 검토합니다.

## 환경에 대한 주의

- **앱 프로세스 CPU(%)는 호스트 CPU 10개 기준 비율입니다.** 앱 안에서 보이는 CPU 수가 10개(바깥 서버 컨테이너의 2코어 한도는 JVM이 모름)라서 지표 10%가 1코어이고 서버 한도는 20%입니다.
- **JVM이 CPU를 10개로 인식합니다.** dev 서버(2 vCPU)는 JVM이 2개로 인식하므로 GC·컴파일 스레드 수가 다릅니다. 영향은 측정하지 않았습니다.
- **MySQL의 `performance_schema`가 꺼져 있어** 쿼리별 누적 시간 통계를 볼 수 없었습니다. 쿼리 시간은 `EXPLAIN ANALYZE`로 개별 확인했습니다.

## 확인해 볼 실험

| 확인 대상 | 실험 | 알 수 있는 것 |
|---|---|---|
| 트랜잭션 제어 문장 | 앱 설정으로 오토커밋 전환과 읽기 전용 전파 문장을 끄고 장바구니 조회를 같은 속도에서 재측정 | 요청당 SQL 수와 p95가 얼마나 줄어드는지 |
| 인증 세션 갱신 | 갱신 간격을 제한한 앱으로 재측정 | 인증 쓰기가 응답 시간에 주는 비중 |
| 지금 뜨는 할인 캐시 | 짧은 시간 캐시를 둔 앱으로 재측정 | 캐시 전후 응답 시간 차이 |
| 알림 소비 | 파티션 수와 소비 방식을 바꿔 재측정 | 알림 저장 시간이 줄어드는 정도 |
