# 웹훅 속도 부하 테스트: 기준선

상태: 초안 · 측정일: 2026-11-05 · 도메인 담당자: 최용범

- 근거 자료: 스크립트 [`scenarios/webhook/webhook-burst.js`](../../../scenarios/webhook/webhook-burst.js), 서명 [`lib/webhook.js`](../../../lib/webhook.js), 표는 [`tools/summarize.py`](../../../tools/summarize.py)로 만들었습니다. 환경과 실행 방법은 [README.md](../../../README.md)를 따릅니다. 원본 결과 파일은 저장소에 두지 않습니다.
- 미정 항목: 합격선과 목표 부하, 측정한 앱 커밋 해시와 이 저장소의 커밋 해시.

## 1. 대상

| 항목 | 내용 |
|---|---|
| API | POST /api/webhooks/portone |
| 호출 주체 | PortOne 서버 (이 측정에서는 k6가 서명한 요청을 직접 보냄) |
| 인증 | 헤더 서명 |

## 2. 측정 조건

- 결제와 매칭되지 않는 결제 완료(`Transaction.Paid`) 웹훅을 요청마다 새 webhook-id로 보냅니다. 앱은 서명을 검증하고 웹훅을 DB에 기록한 뒤 결제를 못 찾아 무시합니다(결제 조회·PG 호출 없음). 결제 상태를 바꾸는 웹훅은 측정하지 않았습니다.
- 회차마다 끝난 뒤 DB에서 웹훅 기록 수가 200 응답 수 이상이고(자동 중단 때 처리 중이던 요청이 더해짐), 모두 무시(IGNORED) 상태이며 중복 id가 없음을 확인했습니다.
- 회차마다 되돌리기 SQL로 웹훅 기록을 지운 뒤 시작했습니다.

## 3. 부하 조건

| 항목 | 값 |
|---|---|
| 초당 요청 수 | 0에서 시작해 200 → 500 → 1,000 → 2,000건으로 단계마다 60초 동안 직선으로 올림 |
| 자동 중단 | 못 따라간 요청 20,000건 초과, 또는 누적 p95 2,000ms 초과 |
| 반복 | 3회, 회차 사이 45초 쉼. 먼저 가볍게 돌려 확인 |

각 단계의 숫자는 그 단계 끝에서 도달하는 속도입니다. 2,000건 단계는 1,000건에서 2,000건까지 올라가는 60초라 평균은 약 1,500건입니다.

## 4. 실행 방법

```bash
DB_USER=<사용자> DB_PASSWORD=<비밀번호> ./tools/run-stateful.sh \
  --reset scenarios/webhook/webhook-reset.sql --verify scenarios/webhook/webhook-verify.sql -- \
  -e RATES=200,500,1000,2000 scenarios/webhook/webhook-burst.js
python3 tools/summarize.py --prefix webhook-burst --last 3 --steps 200:60,500:60,1000:60,2000:60 --uri /api/webhooks/portone --method POST
```

## 5. 결과

### 5-1. 회차별 전체 결과

세 회차 모두 2,000건 단계에서 못 따라간 요청이 20,000건을 넘어 자동 중단됐습니다. 실패율은 0%(응답 모두 200)이고 5xx는 없었습니다. 아래 값에는 한계를 넘긴 구간이 섞여 있습니다.

| 회차 | p50 | p90 | p95 | p99 | 최대 | 요청 수 | 못 따라간 요청 | DB 기록 | 시작 전 부하 평균(1분) |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 8ms | 284ms | 401ms | 1,339ms | 3,346ms | 107,875 | 20,814 | 108,174 | 3.95 |
| 2 | 5ms | 262ms | 307ms | 674ms | 2,035ms | 129,347 | 20,947 | 129,558 | 4.23 |
| 3 | 5ms | 244ms | 277ms | 695ms | 2,028ms | 141,623 | 20,370 | 141,923 | 3.31 |

- DB 기록 수가 요청 수보다 211–300건 많은 것은 자동 중단 시점에 처리 중이던 요청이 더해졌기 때문으로 보입니다(가상 사용자 최대 300명). 200 응답이 기록되지 않은 경우는 없었습니다.
- 모든 회차의 시작 전 호스트 부하 평균이 3.3–4.2로, 앞선 읽기 측정(1–2)보다 높았습니다.

### 5-2. 단계별 서버 쪽 지표 (3회 중앙값, 범위는 괄호)

이 표는 이 환경에서 관찰한 값입니다. 커넥션 풀·MySQL 스레드·CPU 같은 포화 지표는 환경에 따라 달라 dev의 값으로 쓰지 않습니다.

단계 구간은 요청 시작 시각에서 추정해 경계에 ±10초 정도 오차가 있습니다.

| 지표 | 200건 | 500건 | 1,000건 | 2,000건 |
|---|---|---|---|---|
| 앱 처리 속도 평균(건/초) | 87 (85–90) | 323 (319–327) | 704 (697–712) | 1,032 (689–1,156) |
| 앱 p95(ms, 구간 최대) | 13 (11–15) | 2 (2–29) | 22 (9–169) | 1,230 (610–1,759) |
| 앱 p99(ms, 구간 최대) | 23 (13–79) | 5 (5–74) | 68 (20–207) | 1,730 (1,704–2,105) |
| 커넥션 풀 사용 중(최대 10) | 0 (0–1) | 1 (1–5) | 8 (4–10) | 10 (10–10) |
| 커넥션 풀 기다리는 요청 | 0 (0–0) | 0 (0–0) | 0 (0–19) | 190 (190–190) |
| MySQL 실행 중 스레드 | 3 (3–3) | 3 (3–4) | 9 (5–12) | 12 (12–12) |
| 요청 1건당 SQL 문(트랜잭션 제어 포함) | 14.5 (14.5–16.8) | 14.7 (14.7–15.9) | 14.8 (14.8–15.7) | 14.8 (14.7–15.7) |
| 앱 프로세스 CPU(%) | 1.4 (1.2–2.7) | 2.8 (2.8–6.8) | 7.9 (7.4–11.0) | 17.5 (15.9–18.9) |
| GC 멈춤(시간 중 %) | 0.8 (0.1–2.7) | 0.2 (0.1–4.3) | 0.2 (0.2–2.3) | 6.9 (0.4–8.6) |

요청 1건당 SQL 문은 MySQL이 받은 전체 문장 수를 앱이 받은 요청 수로 나눈 값이라 트랜잭션 시작·종료 문장을 포함합니다.
앱 프로세스 CPU(%)는 호스트 CPU 10개 기준 비율입니다(10% = 1코어). 서버 컨테이너의 한도는 2코어라서 20%가 한도입니다.

- 500건 단계까지 p95 2ms였고, 1,000건 단계에서 p95 22ms(구간 최대 169ms), 2,000건 단계에서 p95 1,230ms로 늘었습니다. 이 환경에서 관찰한 값이며 dev에서도 같다는 보장은 없습니다.
- 요청 1건당 SQL 문이 약 15개입니다.
