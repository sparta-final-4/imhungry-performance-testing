# 장바구니 담기 정확성 테스트: 기준선 (같은 상품 동시 담기)

상태: 초안 · 측정일: 2026-11-05 · 도메인 담당자: 장준혁

- 근거 자료: 스크립트 [`scenarios/cart-add/cart-add-accuracy.js`](../../../scenarios/cart-add/cart-add-accuracy.js), DB 확인 [`cart-add-verify.sql`](../../../scenarios/cart-add/cart-add-verify.sql), 되돌리기 [`cart-add-reset.sql`](../../../scenarios/cart-add/cart-add-reset.sql). 환경과 실행 방법은 [README.md](../../../README.md)를 따릅니다. 원본 결과 파일은 저장소에 두지 않습니다.
- 미정 항목: 합격선, 측정한 앱 커밋 해시와 이 저장소의 커밋 해시.
- 이 보고서는 장바구니 담기 동시 충돌 처리를 고치기 전 앱의 기준선입니다.

## 1. 대상

| 항목 | 내용 |
|---|---|
| API | POST /api/cart-items |
| 상황 | 같은 회원이 같은 상품을 동시에 여러 번 담음 (비어 있는 장바구니의 첫 담기 포함) |
| 로그인 | 필요 (회원 쿠키) |
| 확인 대상 | 최종 수량이 성공한 요청 수와 같은지, 서버 오류(5xx)가 있는지, 장바구니·항목 중복 |

## 2. 측정 조건

- 테스트 회원 20명이 각자 같은 상품(상품 17)을 수량 1로 10번씩, 같은 순간에 담았습니다(총 200건).
- 장바구니가 비어 있는 상태에서 시작해 첫 담기의 동시 생성까지 재현했습니다.
- 응답이 아니라 DB 최종 상태로 판단했습니다. 끝난 뒤 그 상품의 항목 수와 수량 합을 읽고 성공(2xx) 요청 수와 비교했습니다.
- 회차마다 되돌리기 SQL로 테스트 회원의 장바구니를 비운 뒤 시작했습니다.

## 3. 실행 방법

```bash
DB_USER=<사용자> DB_PASSWORD=<비밀번호> ./tools/run-stateful.sh \
  --reset scenarios/cart-add/cart-add-reset.sql --verify scenarios/cart-add/cart-add-verify.sql -- \
  scenarios/cart-add/cart-add-accuracy.js
```

## 4. 결과

3회 모두 기대(수량 합 = 성공 건수, 5xx 0건)를 만족하지 못했습니다.

| 회차 | 요청 | 성공(2xx) | 서버 오류(5xx) | DB 수량 합 | 유실(성공 − 수량 합) | 항목 수 | 중복 장바구니 | 중복 항목 | p95 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 200 | 190 | 10 | 163 | 27 | 20 | 0 | 0 | 369ms |
| 2 | 200 | 197 | 3 | 170 | 27 | 20 | 0 | 0 | 205ms |
| 3 | 200 | 195 | 5 | 159 | 36 | 20 | 0 | 0 | 257ms |

- 서버 오류가 회차마다 3–10건 났습니다(회원 20명 중 첫 담기를 동시에 새로 만들다 제약 충돌이 난 것으로 보이며, 원인 로그는 확인하지 않았습니다).
- 성공으로 응답한 요청 중 27–36건의 수량이 DB에 반영되지 않았습니다(갱신 유실). 회원별 수량은 최소 5, 최대 10이었습니다.
- 장바구니와 항목 중복은 없었습니다.

## 5. 다음에 할 것

- 첫 담기 동시 생성 충돌(5xx)을 막는 수정을 반영하고 같은 조건으로 다시 측정해 5xx 0건을 확인합니다.
- 갱신 유실(성공 − 수량 합)은 허용 여부를 정한 대로 다룹니다. 허용하지 않기로 하면 같은 조건으로 다시 측정해 유실 0을 확인합니다.
