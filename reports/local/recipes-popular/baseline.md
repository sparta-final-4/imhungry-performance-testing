# 이번 달 많이 만든 레시피 부하 테스트: 기준선 (캐시 없음, 캐시 적용)

상태: 초안 · 측정일: 2026-11-04 · 도메인 담당자: 이현정 · 캐시 없음이 개선 전 기준선이고, 캐시 적용은 현재 소스코드에 이미 들어 있는 개선입니다.

- 근거 자료: 스크립트 [`scenarios/recipes-popular/recipes-popular.js`](../../../scenarios/recipes-popular/recipes-popular.js), 환경과 실행 방법은 [README.md](../../../README.md), 표는 [`tools/summarize.py`](../../../tools/summarize.py)로 만들었습니다. 원본 결과 파일(HTML·JSON·텍스트)은 저장소에 두지 않습니다.
- 미정 항목: 합격선과 목표 부하(후보 상태), 측정한 앱 커밋 해시와 이 저장소의 커밋 해시.

## 1. 대상과 선정 이유

| 항목 | 내용 |
|---|---|
| API | GET /api/recipes/popular?size=6 |
| 화면 | 메인 화면 이번 달 많이 만든 레시피 |
| 선정 이유 | 로그인 없이 모든 방문자가 호출 / 최근 30일 요리 기록 집계에 레시피·후기를 조합하는 조회 / 결과가 모두에게 같고 하루 단위로만 바뀜 |
| 적용된 방법 | Redis 캐시 24시간, 후기 작성 시 캐시 비우기 |

## 2. 측정 조건

- 데이터: 요리 기록 약 10만 건(최근 30일 약 98,000건), 레시피 1,693개입니다.
- 캐시 없이 측정하는 방법: `run-no-cache.sh`가 측정하는 동안 캐시 키(`recipe:popular::6`)를 쉬지 않고 지웁니다. 서버가 캐시를 채운 직후에 삭제가 따라오므로 일부 요청은 캐시에서 처리됩니다(적중).
- 시작 전 호스트 부하 평균(1분)은 5-2의 회차별 표에 적었습니다.
- 캐시 적용은 캐시 없음 3회에 이어 같은 세션에서 앱을 다시 띄우지 않고 측정했습니다. 캐시 키를 지우는 동작을 멈추면 첫 요청이 캐시를 채웁니다(캐시 적용 1회차 최대 73ms).

## 3. 부하 조건

| 항목 | 값 |
|---|---|
| 동시 사용자 | 20명 (10초 동안 올림 → 30초 유지 → 5초 내림) |
| 요청 간격 | 요청이 끝난 뒤 1초 쉼 |
| 합격선 | p95 < 500ms, 실패율 < 1% |
| 반복 | 캐시 없음 3회, 캐시 적용 3회. 회차 사이 15초 쉼 |

합격선은 후보일 뿐 확정이 아닙니다.

## 4. 실행 방법

```bash
./tools/run-no-cache.sh scenarios/recipes-popular/recipes-popular.js   # 캐시 없음
./tools/run.sh scenarios/recipes-popular/recipes-popular.js            # 캐시 적용
python3 tools/summarize.py --prefix recipes-popular --last 3 --steps 전체:45 --uri /api/recipes/popular --method GET
```

환경 올리는 방법은 [README](../../../README.md)의 `따라 하기`를 따릅니다.

| p95 | **4,094ms** (합격선 500ms 초과) | **5.9ms** (합격선 이내) |
| p99 | 4,775ms | 6.6ms |

### 5-3. 캐시 적중

Redis의 `keyspace_hits`(적중), `keyspace_misses`(미스)가 회차마다 늘어난 양입니다. 합이 회차별 요청 수와 같았습니다.

| 구분 | 회차 | 적중(hit) | 미스(miss) | 적중률 |
|---|---|---|---|---|
| 캐시 없음 | 1 | 2 | 237 | 0.8% |
| 캐시 없음 | 2 | 3 | 242 | 1.2% |

- 캐시 없음의 적중은 서버가 캐시를 채운 직후 삭제가 따라오기 전에 들어온 요청입니다. 99% 가까이는 DB를 거쳤습니다.
- 캐시 없음 3회차와 캐시 적용은 종료 시점의 Redis 값이 기록되지 않아 적중 수를 적지 않았습니다. 캐시 적용은 모든 요청이 5ms대로 응답했고 캐시 키를 비운 직후 첫 요청만 느렸습니다.
- 캐시 키를 비운 직후 첫 요청은 45–84ms(3번 측정), 다음 요청은 2.8ms였습니다.

## 6. 해석

### 6-1. 관찰한 것

- 캐시 없음에서는 처리량이 초당 약 5건에서 올라가지 않고 응답 시간만 길어졌습니다(p50 2.8초). 같은 시간에 DB 커넥션이 모두 사용 중(10/10)이었고 GC 멈춤은 거의 없었습니다.
- 요청 하나만 보내면 느리지 않았습니다. 캐시를 비운 뒤 단독 요청 3번이 45–84ms였습니다. 20명이 동시에 보낼 때만 p50이 2.8초로 늘었습니다.
- 집계 쿼리의 실행 계획은 인덱스 하나를 처음부터 끝까지 읽습니다(약 99,876행 추정). 전체 100,087행 중 최근 30일이 97,988행이어서 날짜 조건이 거의 걸러 내지 못합니다.
- 캐시 적용에서는 모든 요청이 캐시에서 처리되어 DB 커넥션 풀이 비어 있었고(0/10), 요청 1건당 쿼리는 0.2건이었습니다.

### 6-2. 의심되는 원인 (확인은 안 됨)

- 요청 하나만 보내면 45–84ms인데 동시 20명에서 p50이 2.8초가 되는 이유는 확인하지 못했습니다. 이 환경에서 관찰한 값이며 dev에서도 같다는 보장은 없습니다.
- 날짜(`created_at`)로 범위를 좁히는 인덱스가 없어서 집계가 거의 모든 행을 읽는 것이 한 요인일 가능성이 있습니다.

### 6-3. 확인하지 못한 것

- 동시 실행에서 쿼리 1건당 CPU 사용량이 늘어나는 이유, 쿼리 단독 실행 계획의 상세(실행 중 읽은 행 수, 임시 테이블 사용).
- 캐시가 만료되거나 후기 작성으로 비워진 직후 여러 요청이 동시에 몰릴 때의 응답 시간(캐시 적용 측정은 캐시가 채워진 상태에서만 측정했습니다).
- 요청 1건당 SQL 수(캐시 없음), 추적(구간별 시간).
- dev 환경의 값. 이 숫자는 로컬에서 측정한 값입니다.
