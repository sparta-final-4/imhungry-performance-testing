# 레시피 분류 조회 부하 테스트: 기준선 (캐시 없음, 캐시 적용)

상태: 초안 · 측정일: 2026-11-04 · 도메인 담당자: 강준모 · 캐시 없음이 개선 전 기준선이고, 캐시 적용은 현재 소스코드에 이미 들어 있는 개선입니다.

- 근거 자료: 스크립트 [`scenarios/recipe-classifications/recipe-classifications.js`](../../scenarios/recipe-classifications/recipe-classifications.js), 환경과 실행 방법은 [README.md](../../README.md), 표는 [`tools/summarize.py`](../../tools/summarize.py)로 만들었습니다. 원본 결과 파일은 저장소에 두지 않습니다.
- 미정 항목: 합격선과 목표 부하, 측정한 앱 커밋 해시와 이 저장소의 커밋 해시.

## 1. 대상과 선정 이유

| 항목 | 내용 |
|---|---|
| API | GET /api/recipes/classifications |
| 화면 | 레시피 분류·필터 |
| 로그인 | 필요 없음 |
| 응답 | 요리 종류 7개와 카테고리 목록, 433바이트. 모든 요청의 응답이 같음 |
| 처리 | 레시피 테이블에서 요리 종류와 카테고리의 중복 없는 값을 조회(조회 2번) |
| 적용된 방법 | Redis 캐시 1시간, 레시피 등록·수정 때 캐시 비우기 |

## 2. 측정 조건

- 레시피 1,693개입니다.
- 캐시 없이 측정하는 방법: `run-no-cache.sh`가 측정하는 동안 캐시 키(`recipe:classifications::all`)를 쉬지 않고 지웁니다. 서버가 캐시를 채운 직후에 삭제가 따라오므로 일부 요청은 캐시에서 처리될 수 있습니다.
- 캐시 적용은 캐시 없음 3회에 이어 같은 세션에서 앱을 다시 띄우지 않고 측정했습니다.
- 시작 전 호스트 부하 평균(1분)은 5-1의 회차별 표에 적었습니다.

## 3. 부하 조건

| 항목 | 값 |
|---|---|
| 초당 요청 수 | 0에서 시작해 200 → 500 → 1,000 → 2,000건으로 단계마다 60초 동안 직선으로 올림, 마지막에 10초 동안 0으로 내림(합계 약 172,000건) |
| 자동 중단 | 못 따라간 요청 20,000건 초과, 또는 누적 p95 2,000ms 초과 |
| 반복 | 캐시 없음 3회, 캐시 적용 3회. 회차 사이 60초 쉼. 먼저 가볍게 돌려 확인(p95 9.5ms, 실패 0) |

각 단계의 숫자는 그 단계 끝에서 도달하는 속도입니다. 2,000건 단계는 1,000건에서 2,000건까지 올라가는 60초라 평균은 약 1,500건입니다.

## 4. 실행 방법

```bash
./tools/run-no-cache.sh -e RATES=200,500,1000,2000 scenarios/recipe-classifications/recipe-classifications.js   # 캐시 없음
./tools/run.sh -e RATES=200,500,1000,2000 scenarios/recipe-classifications/recipe-classifications.js            # 캐시 적용
python3 tools/summarize.py --prefix recipe-classifications --last 3 --steps 200:60,500:60,1000:60,2000:60 --uri /api/recipes/classifications --method GET
```

캐시 없음과 캐시 적용은 결과 파일의 시각으로 `--since`, `--until`을 줘서 나눠 만듭니다.

## 6. 해석

### 6-1. 관찰한 것

- 캐시 없음에서는 1,000건 단계까지 p95 중앙값이 31ms 이하였고, 2,000건 단계에서 커넥션 풀이 가득 차(10/10) 대기가 최대 187건까지 쌓이며 p95가 최대 211ms로 늘었습니다. 중앙값으로는 p95 181ms, 풀 대기 178건입니다.
- 캐시 적용에서는 2,000건 단계까지 p95 1ms, 커넥션 풀 0/10, 못 따라간 요청 0건이었습니다. 앱 CPU는 2,000건 단계에서 3.2%로 캐시 없음의 16.0%보다 낮았습니다.
- 캐시 키를 비운 직후 단독 요청은 2.7–4.5ms(3번 측정)였고 응답은 433바이트입니다. 요청 하나는 캐시 없이도 빠릅니다.
- 캐시 없음에서 요청 1건당 SQL 문이 6.7(200건 단계)에서 5.2(2,000건 단계)로 줄었습니다. 부하가 커질수록 삭제가 따라오기 전에 캐시에서 처리되는 요청의 비율이 늘었을 가능성이 있습니다. 적중 수는 기록하지 않아 확인하지 못했습니다.

### 6-2. 확인하지 못한 것

- 캐시 없음의 실제 캐시 적중 비율(Redis 적중·미스를 회차별로 기록하지 못함).
- 캐시가 만료되거나 레시피 등록으로 비워진 직후 여러 요청이 동시에 몰릴 때의 응답 시간.
- 캐시 없음 회차가 거듭될수록 느려진 이유.
- dev 환경의 값. 이 숫자는 로컬에서 측정한 값입니다.
