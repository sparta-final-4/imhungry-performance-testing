# 장바구니 조회 부하 테스트: 기준선

상태: 초안 · 측정일: 2026-11-05 · 도메인 담당자: 장준혁

- 근거 자료: 스크립트 [`scenarios/cart-read/cart-read.js`](../../scenarios/cart-read/cart-read.js), 표는 [`tools/summarize.py`](../../tools/summarize.py)로 만들었습니다. 환경과 실행 방법은 [README.md](../../README.md)를 따릅니다. 원본 결과 파일은 저장소에 두지 않습니다.
- 미정 항목: 합격선과 목표 부하, 측정한 앱 커밋 해시와 이 저장소의 커밋 해시.

## 1. 대상

| 항목 | 내용 |
|---|---|
| API | GET /api/cart-items |
| 화면 | 장바구니 |
| 로그인 | 필요 (회원 쿠키) |

## 2. 측정 조건

- 테스트 회원 100명이 각자 상품 3개(상품 16, 17, 19)를 장바구니에 담은 상태입니다. 요청마다 회원을 돌아가며 고릅니다.
- 로그인과 장바구니 준비는 측정 시간에 들어가지 않습니다.
- 상품 조회에 진행 중 할인 조회가 더해집니다.
- 앱은 이 API만 호출했습니다. 캐시는 없습니다.

## 3. 부하 조건

| 항목 | 값 |
|---|---|
| 초당 요청 수 | 0에서 시작해 200 → 500 → 1,000 → 2,000건으로 단계마다 60초 동안 직선으로 올림, 마지막에 10초 동안 0으로 내림(합계 약 172,000건) |
| 자동 중단 | 못 따라간 요청 20,000건 초과, 또는 누적 p95 2,000ms 초과 |
| 반복 | 3회, 회차 사이 60초 쉼. 먼저 가볍게 돌려 확인 |

각 단계의 숫자는 그 단계 끝에서 도달하는 속도입니다. 2,000건 단계는 1,000건에서 2,000건까지 올라가는 60초라 평균은 약 1,500건입니다.

## 4. 실행 방법

```bash
./tools/run.sh -e RATES=200,500,1000,2000 scenarios/cart-read/cart-read.js
python3 tools/summarize.py --prefix cart-read --last 3 --steps 200:60,500:60,1000:60,2000:60 --uri /api/cart-items --method GET
```

## 5. 결과

### 5-1. 회차별 전체 결과

세 회차 모두 2,000건 단계에서 못 따라간 요청이 20,000건을 넘어 자동 중단됐습니다. 실패율은 0%입니다. 아래 값에는 한계를 넘긴 구간이 섞여 있어서, 개선 전후 비교는 5-2의 단계별 값으로 합니다.

| 회차 | p50 | p90 | p95 | p99 | 최대 | 요청 수 | 못 따라간 요청 | 실패율 | 시작 전 부하 평균(1분) |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 3ms | 304ms | 391ms | 547ms | 1,193ms | 129,428 | 20,630 | 0% | 1.46 |
| 2 | 2ms | 329ms | 394ms | 568ms | 2,189ms | 126,592 | 20,427 | 0% | 2.12 |
| 3 | 2ms | 340ms | 399ms | 561ms | 1,459ms | 125,921 | 20,340 | 0% | 1.20 |

세 회차의 p95 편차는 약 2%(391–399ms)입니다. 모든 회차를 CPU 유휴율 95% 이상인 호스트에서 시작했습니다.

### 5-2. 단계별 서버 쪽 지표 (3회 중앙값, 범위는 괄호)

단계 구간은 요청 시작 시각에서 추정해 경계에 ±10초 정도 오차가 있습니다.

| 지표 | 200건 | 500건 | 1,000건 | 2,000건 |
|---|---|---|---|---|
| 앱 처리 속도 평균(건/초) | 87 (78–88) | 320 (306–321) | 700 (676–702) | 1,024 (989–1,050) |
| 앱 p95(ms, 구간 최대) | 12 (12–15) | 2 (2–3) | 4 (3–4) | 440 (438–500) |
| 앱 p99(ms, 구간 최대) | 14 (13–21) | 5 (4–7) | 7 (7–7) | 582 (577–1,670) |
| 커넥션 풀 사용 중(최대 10) | 1 (1–6) | 1 (1–3) | 3 (3–3) | 10 (10–10) |
| 커넥션 풀 기다리는 요청 | 0 (0–0) | 0 (0–0) | 0 (0–0) | 190 (190–190) |
| MySQL 실행 중 스레드 | 2 (2–3) | 3 (3–3) | 4 (4–4) | 5 (3–8) |
| 요청 1건당 SQL 문(트랜잭션 제어 포함) | 25.1 (25.0–25.1) | 25.5 (25.5–25.5) | 25.6 (25.6–25.6) | 25.9 (25.8–26.0) |
| 앱 프로세스 CPU(%) | 14.2 (12.2–15.8) | 4.0 (3.9–4.2) | 9.3 (9.3–9.9) | 21.4 (21.4–21.5) |
| GC 멈춤(시간 중 %) | 0.3 (0.1–1.5) | 0.2 (0.2–0.2) | 0.6 (0.4–0.7) | 3.4 (2.6–3.5) |

요청 1건당 SQL 문은 MySQL이 받은 전체 문장 수를 앱이 받은 요청 수로 나눈 값이라 트랜잭션 시작·종료 문장을 포함합니다.

- 1,000건 단계까지는 커넥션 풀 사용 3/10, 대기 0, p95 4ms였습니다.
- 한계는 1,000건/초 근처입니다. 2,000건 단계에서 앱 처리 속도가 약 1,024건/초에서 더 오르지 않고, 풀이 가득 차(10/10) 요청이 190건씩 기다렸으며 p95가 440ms로 늘었습니다. 앱 CPU는 21%였습니다.
- 요청 1건당 SQL 문이 약 25–26개로, 장바구니 항목 3개짜리 조회에 비해 많습니다.
- 200건 단계의 앱 CPU 14.2%는 앞의 준비 작업(로그인·장바구니 준비) 구간이 섞인 값일 가능성이 있습니다.
