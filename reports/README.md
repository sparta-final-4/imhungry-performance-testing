# 부하 테스트 보고서

측정이 끝난 API의 보고서만 올립니다.

- 스크립트와 실행 방법, 환경 만드는 방법은 [README.md](../README.md)에 있습니다.
- 2차 측정(2026-11-06부터)의 보고서는 `dev/`에 있습니다. 그 아래 폴더 이름은 스크립트 폴더 이름과 같게 만듭니다(`recipes-popular/`, `orders/`, `cart-items/` …). 환경이 다른 숫자는 섞지 않습니다.
- 1차 측정(2026-11-03–05)의 로컬·dev 보고서는 `archive-1차/`(`local/`, `dev/`)에 옮겨 두었습니다.
- 로컬 숫자는 dev.imhungry.click과 같은 서버 구성(앱, 데이터, 검색)에 모니터링 서버를 추가한 환경에서 측정한 값이고, 같은 조건의 개선 전후 비교에만 씁니다. dev.imhungry.click 숫자는 집 회선에서 인터넷을 거쳐 보낸 값이라 응답 시간에 그 왕복 시간이 들어 있습니다.
- 2026-11-06부터 측정은 dev.imhungry.click에서만 하고, 보고서는 `dev/<API 폴더>/`에 API 하나에 측정 방식마다 하나씩 씁니다. 같은 순간 몰림(N명이 같은 순간 한 번씩)은 `<API>-burst.md`, 유지(N명이 정한 시간 동안 계속 요청)는 `<API>-hold.md`입니다. 두 방식은 같은 사용자 수라도 서버가 동시에 받는 요청 수가 달라 숫자를 서로 비교하지 않습니다. 측정 시각(시작과 끝)과 그때 소스코드 저장소 `dev` 브랜치 커밋을 적어 둡니다.
- k6 결과 화면(HTML)은 `tools/share-html.py`로 로컬 경로를 지운 사본을 보고서 옆에 함께 둡니다(로컬, dev.imhungry.click 모두). 보고서의 근거 자료에서 회차 순서대로 링크합니다.
- 같은 순간 몰림(`-burst.md`)은 `tools/run-burst.sh`가 남긴 회차별 표(`rounds.csv`, 예열 1회 뒤 3회)를 그대로 넣습니다. 가상 사용자 1,000명이 같은 시각에 한 번씩 보내고, 대상 요청의 p95가 0.67초 이하이고 실패가 0이면 통과입니다. 최대값은 같은 시각에 보내고 마지막 응답까지 걸린 시간입니다. 첫 요청에는 HTTPS 연결 수립이 들어갑니다(`PREWARM=1`이면 연결을 미리 맺어 둡니다).
- 유지(`-hold.md`)는 `tools/run-hold.sh`가 남긴 단계별 표(`steps.csv`)를 넣습니다. 사용자 수와 유지 시간은 측정 전에 정해 보고서에 적습니다.
- 로그인 없이 열린 API는 로그인 안 함과 로그인 함 두 조건을 한 보고서에 나란히 둡니다.
- 각 보고서는 질문, 상황, 기준, 대상, 측정 조건, 실행 방법, 결과, 분석 순서입니다. 분석은 측정한 숫자로 바로 말할 수 있는 것만 쓰고, 계산한 값은 계산이라고, 확인하지 않은 것은 확인하지 않았다고 적습니다. 다음에 할 것은 개선을 맡은 도메인의 보고서에만 씁니다.
- 질문·상황·기준은 각 보고서 앞에 적습니다. 기준은 쓰기(주문하기, 같은 순간 100명)는 p95 1초, 읽기는 p95 0.67초(팀 합의)입니다.

요청 1건의 작업량과 개선 방향(코드·쿼리 → 캐시 → 다른 기술 → 대안)은 [bottleneck-analysis.md](archive-1차/local/bottleneck-analysis.md)에 있습니다.
